# OSCAR 3.11.0 (Amber) Release Overview, Architectural Rationale, and User Guide

OSCAR 3.11.0 (Amber) is engineered for continuous 24/7 operation across multi-year retention windows at large radiation portal monitoring (RPM) sites (up to 50 concurrent RPM and RTSP camera lanes per server) on Ubuntu Server 24.04 x86-64 and Windows 11 x86-64.

This guide summarizes what changed, **why** each major architectural and operational change was implemented, which release artifact to download, and where **new users** and **existing users** should start.

---

## 1. Start Here: Choose Your Path

### Path A — New Users (Fresh Installation)

1. **Choose the right release package** from [GitHub Releases](https://github.com/ORNL/oscar/releases):
   - **Ubuntu Server 24.04 x86-64 (Connected):** Download `oscar-3.11.0.zip`.
   - **Windows 11 x86-64 (Connected):** Download `oscar-3.11.0.zip`.
   - **Windows 11 x86-64 (Air-Gapped / Offline, No Docker Installed Yet):** Download `oscar-3.11.0-windows-x86_64-offline-full.zip` (includes pinned Docker Desktop and WSL 2 installers plus pre-built container images).
   - **Windows 11 x86-64 (Air-Gapped / Offline, Docker Desktop & WSL 2 Already Running):** Download `oscar-3.11.0-windows-x86_64-offline-images.zip`.
2. **Prepare the host and initialize OSCAR:**
   - Follow the step-by-step [Quick Start](../dist/release/QUICKSTART.md) (`.\oscar.bat prepare-host` and `.\oscar.bat init` on Windows 11; `sudo bash oscar.sh init` on Ubuntu 24.04).
   - Review the [Administrator Guide](../dist/release/DEPLOYMENT.md) for static/reserved LAN IPv4 assignment, TLS certificate trust across operator workstations, Tailscale SANs, and optional `single`-snapshot backup configuration.
3. **Configure lanes, views, and operators:**
   - Open the [Operator and Administrator Manual (English)](https://github.com/ORNL/osh-oakridge-modules/blob/main/services/sensorhub-service-oscar/src/main/resources/com/botts/impl/service/oscar/i18n/README.md) — or the [Español](https://github.com/ORNL/osh-oakridge-modules/blob/main/services/sensorhub-service-oscar/src/main/resources/com/botts/impl/service/oscar/i18n/README_es.md), [Français](https://github.com/ORNL/osh-oakridge-modules/blob/main/services/sensorhub-service-oscar/src/main/resources/com/botts/impl/service/oscar/i18n/README_fr.md), or [Ελληνικά](https://github.com/ORNL/osh-oakridge-modules/blob/main/services/sensorhub-service-oscar/src/main/resources/com/botts/impl/service/oscar/i18n/README_el.md) editions (also published as standalone PDFs on each GitHub Release) — to configure lanes, thresholds, users, adjudication workflows, and reports.
   - Follow the 16 single-task (< 2 min) captioned screen recordings and 3-to-4-step reference blocks in [How-To Video Guides](VIDEO_GUIDES.md) (`ORNL/oscar-video-guides`).

### Path B — Current Users Running `pre-3.11.0` (`3.10.0`, `3.9.x`, `3.8.x`, or Earlier)

OSCAR 3.11.0 introduces a data-checksummed PostgreSQL 16 cluster, the `PARQUET_PRIMARY` tiered observation store, deployment-bound storage-root identity markers, and the direct daily-file journal. **To protect existing deployments from unexpected data mutations, `upgrade` never silently converts a `pre-3.11.0` database or overwrites a saved `config.json`.**

Choose one of two explicit rollout options depending on site requirements:

1. **Recommended for Full 3.11.0 Multi-Year Storage & Performance (`PARQUET_PRIMARY`):**
   - Preserve the existing `pre-3.11.0` deployment read-only after taking its supported backup/export.
   - Deploy OSCAR 3.11.0 into a clean directory and fresh storage roots using `oscar init` ([Quick Start](../dist/release/QUICKSTART.md)) so PostgreSQL initializes with `--data-checksums`, `PARQUET_PRIMARY` 30-minute stage partitions, the direct daily-file journal, and five-frame JPEG media retention.
   - Re-import your site's lane CSV (updated with optional `Views` column assignments; see [Operational Views](OPERATIONAL_VIEWS.md)), click **Apply** and **Save Configuration** in SensorHub Admin, and run a supported `oscar restart`. Migrate historical records separately only if site policy requires it.
2. **Retaining an Existing Legacy Volume Set In-Place (Without `PARQUET_PRIMARY` Re-Initialization):**
   - Read the **3.11.0 storage migration boundary** section of the [Administrator Guide](../dist/release/DEPLOYMENT.md) and **Existing pre-3.11.0 deployments** in [Storage Operations](STORAGE_OPERATIONS.md) before running any command.
   - Only after verifying that the existing named Docker volumes and any nonempty archive/backup directories belong to that exact deployment, use the explicit one-time adoption flags (`--adopt-legacy-volumes` / `-AdoptLegacyVolumes` and, when applicable, `--adopt-legacy-storage-roots` / `-AdoptLegacyStorageRoots`). Retain the resulting `.oscar-volume-adoption` receipt alongside `.env`, `secrets/`, and `tls/`.

### Path C — Current Users Upgrading an Existing `3.11.0+` Same-Profile Deployment

1. If `OSCAR_BACKUP_MODE=single` is enabled, run and verify a fresh snapshot (`oscar backup` and `oscar backup-verify`; see [Backup and Restore](BACKUP_RESTORE.md)).
2. Extract the new release ZIP into a **clean sibling directory** (never extract over an existing release folder).
3. Copy **only** `.env`, `secrets/`, and `tls/` (plus `.oscar-volume-adoption` if previously created) from the prior release directory into the new directory.
4. Run `.\oscar.bat upgrade` (Windows) or `sudo bash oscar.sh upgrade` (Ubuntu). Setup validates volume/root ownership, runs the idempotent offline daily-file index check under the storage lock, and force-recreates all containers while preserving `oscar_oscar_state`, `oscar_postgres_data`, and external archive/backup roots. See **Upgrade** in [Administrator Guide](../dist/release/DEPLOYMENT.md).

## 2. Major New Features and Why They Were Implemented

### 2.1 `PARQUET_PRIMARY` Tiered Observation Storage, Startup Route Reconciliation & DuckDB Query Federation
- **What changed:** All **12** high-volume immutable detector, status, report, and EML streams (`gammaCounts`, `gammaThreshold`, `neutronCounts`, `setupGamma`, `setupNeutron`, `speed`, `backgroundReport`, `foregroundReport`, `status`, `emlContextual`, `emlScanContextual`, `emlAnalysis`) write into UTC-aligned 30-minute `LOGGED` PostgreSQL child partitions (`osg_*`). Once a 30-minute window closes (plus a 5-minute clock-skew/late-arrival safety delay), a background worker exports the window into Hive-partitioned (`date=YYYY-MM-DD/profile=RAW_GATED`), Zstandard-compressed Apache Parquet files, verifies exact row count, UUID digest, and SHA-256 parity, and retires the entire staging table in `O(1)` metadata time (`NO INHERIT` + `DROP TABLE`). On startup, OSCAR automatically reconciles `oscar_obs_storage_route` entries (`reconcileRoutes()`) so any datastream matching the 12 allowlisted outputs is upgraded to `immutable=true`, reclaims empty expired `ATTACHED` and leftover `DETACHED` stage partitions (`reclaimEmptyOrRetiredStages()`), and retroactively exports any legacy unarchived rows sitting in the parent `ONLY oscar.obs` table for newly-promoted immutable streams into verified Parquet generations before deleting the migrated parent rows. Mutable operational records (occupancies/alarms, append-only adjudications, reports, commands, overlays, holds, and system metadata) remain in `ONLY oscar.obs`. Embedded DuckDB transparently federates hot PostgreSQL stages and cold Parquet generations behind standard OpenSensorHub `IObsSystemDatabase` / OGC `ConSys` / CQL2 APIs.
- **Why it was implemented:** On a 50-lane site emitting continuous 1 Hz detector, status, and EML telemetry, leaving `speed`, `status`, `backgroundReport`, `foregroundReport`, or EML streams in the unpartitioned parent table — or retaining detector counts in a single PostgreSQL JSONB table — accumulates millions of rows per day and billions over a 5-year (`1,825-day`) retention horizon. Continuous row-by-row `INSERT` and retention `DELETE` churn caused severe PostgreSQL MVCC dead-tuple bloat, autovacuum I/O contention, WAL amplification, and multi-gigabyte B-tree/GIN index growth. Routing all 12 immutable telemetry streams into 30-minute stage partitions and dropping whole partitions after Parquet parity eliminates row-level `DELETE` bloat completely, compresses cold history ~10–15x in self-describing Parquet, keeps `obs_datastreams` compact (~12–15 MiB with >93% PostgreSQL HOT updates), and speeds up multi-day historical CQL/report scans by ~19x while preserving 100% OpenSensorHub API compatibility.
- **Read more:** [Storage Architecture](STORAGE_ARCHITECTURE.md), [Data Lifecycle Policy](DATA_LIFECYCLE.md), [Cold Archive Format](ARCHIVE_FORMAT.md), and [Storage Operations](STORAGE_OPERATIONS.md).

### 2.2 Exact-Five JPEG Retained Alarm Media & Bounded MP4 Lifecycle
- **What changed:** Completed alarm camera recordings are asynchronously decoded into five deterministic baseline sRGB JPEG keyframes (`FIRST`, `QUARTER`, `MIDDLE`, `THREE_QUARTERS`, `LAST`) verified by a manifest commit marker, with bounded post-roll so even 1-second occupancies capture five frames. Source MP4 clips remain playable during a 24-hour post-publication rollback grace before automatic reclamation (failed or `<5`-frame clips preserve their MP4 indefinitely), and after 30 days secondary frames prune while `MIDDLE` (`frame-03.jpg`) stays online for multi-year event history. The Viewer renders an interactive 5-frame gallery with automatic legacy MP4 fallback.
- **Why it was implemented:** Retaining raw H.264 MP4 video for thousands of alarms across 50 cameras quickly exhausts terabytes of storage, while frame-dropping video re-transcoding was CPU-heavy and fragile on short clips. Extracting five verified JPEGs immediately preserves evidentiary visual context across the entire occupancy trajectory at a tiny fraction of MP4 disk cost, and pruning down to the middle frame after 30 days bounds multi-year media growth predictably.
- **Read more:** [Retained Media v1 Specification](https://github.com/ORNL/osh-oakridge-modules/blob/main/docs/retained-media-v1.md), [Live Video & Recording Guide](LIVE_VIDEO.md), and [Data Lifecycle Policy](DATA_LIFECYCLE.md).

### 2.3 Crash-Recoverable Direct Daily-File Journal (`DailyFileJournalService`)
- **What changed:** Rapiscan, RS350, and Aspect drivers append raw detector records before parsing into a per-lane, length-prefixed, `CRC32C`-verified write-ahead journal on disk, decoupled from historical backlog rendering, with atomic daily CSV + SHA-256 manifest publication, 30-day replay-verified journal cleanup, and live Viewer display of the latest 15 daily-file messages.
- **Why it was implemented:** Legacy daily-file generation reconstructed CSVs from parsed database observations or in-memory buffers, meaning a restart, parser error, or database stall could drop raw vendor messages or cause multi-minute startup spikes across 50 lanes. Direct pre-parse journaling guarantees source-message durability and fast bounded restarts.
- **Read more:** [Daily-File Journal v1 Specification](https://github.com/ORNL/osh-oakridge-modules/blob/main/docs/daily-file-journal-v1.md) and [Storage Architecture](STORAGE_ARCHITECTURE.md).

### 2.4 Opt-In Schema-v2 Single-Snapshot Backup, Self-Contained Restore & Legal Holds
- **What changed:** Fresh deployments default to `OSCAR_BACKUP_MODE=disabled` with `archive_mode=off` (no continuous external WAL archive mount). Administrators can opt into `single` mode on a non-overlapping backup path (`oscar upgrade --backup-mode single --backup-dir ...`), producing an HMAC-SHA-256-verified, `pg_verifybackup`-checked recovery point combining a streamed PostgreSQL base backup (`--wal-method=stream`), OSCAR state, Parquet cold-tier inventory, and AES-256-CBC encrypted credentials behind an atomic `CURRENT` pointer. Observation and generation legal holds (`GENERATION_EXACT`, `HOT_EXACT`, `COLD_RANGE_CONSERVATIVE`) and two-step tokenized cold-archive purges protect evidentiary records across API/UI and CLI operations.
- **Why it was implemented:** Continuous external PostgreSQL WAL archiving on unattended edge servers created silent disk-exhaustion hazards whenever backup media disconnected or filled up, and multi-snapshot local retention multiplied multi-gigabyte cold-archive footprints. Self-contained streamed base backups with `archive_mode=off` eliminate unbounded WAL accumulation while providing cryptographically verified, cross-host-portable disaster recovery (including over NTFS USB SSD or Gigabit LAN; PITR is intentionally out of scope).
- **Read more:** [Backup, Restore, and Recovery Runbook](BACKUP_RESTORE.md) and [Storage Operations](STORAGE_OPERATIONS.md).

### 2.5 URL-Scoped Operational Views, Automatic Tight Lane-Extent Map Zoom, Lane/Camera Status of Health & Built-In Loopback RTSP/HLS Video Resilience
- **What changed:** Administrators can assign lanes to named workstation views (via Admin UI or CSV `Views` column) accessed at `/view/<slug>`, scoping live subscriptions, maps, event tables, statistics, health indicators, and reports. The Dashboard, Map, and Operational View maps automatically zoom tightly to the bounding extent of the active lane markers (`zoomSnap: 0`, `padding: [14, 14]`, immediate `laneSystem` coordinate seeding, and `(0, 0)` Null Island exclusion) so all 4, 25, or 50 configured lanes are clearly visible without overlap or excess padding. A dedicated Status of Health page and compact Dashboard lane pills report independent RPM and camera connectivity, gamma/neutron faults, tamper state, and extended occupancy in bounded 30-second batches. For `rtsp://` and `rtsps://` cameras, OSCAR now embeds and supervises a transparent loopback `mediamtx` RTSP proxy inside the `oscar` container (`127.0.0.1`, keeping real camera URLs unchanged across `config.json`, Admin UI, and CSV imports/exports), deduplicating identical streams to a single upstream TCP camera socket per server, normalizing leading `//` stream paths, verifying upstream readiness before reporting `Online`, reconnecting dropped streams in-place without restarting the SensorHub module, normalizing packet DTS/PTS discontinuities, and coordinating multi-operator shared live HLS leases with keyframe-gated startup.
- **Why it was implemented:** Large ports and facilities divide 50+ lanes across gate-specific operator consoles (`east-gate`, `west-gate`, `pedestrian`, etc.); opening unfiltered real-time MQTT/video feeds for every lane on every workstation wasted browser memory and distracted operators. Physical edge IP cameras also tightly cap concurrent TCP `:554` sessions and emit packet timestamp discontinuities or reject duplicate/malformed RTSP paths, while multiple operators viewing the same lane previously risked stopping each other's shared HLS stream on navigation.
- **Read more:** [Operational Views Guide](OPERATIONAL_VIEWS.md), [Status of Health Guide](STATUS_OF_HEALTH.md), and [Live Video Guide](LIVE_VIDEO.md).

### 2.6 Event UUID Direct Links, Full-Database Adjudication Code Filtering, QR Alarm Transfer & Serialized National Statistics
- **What changed:** Every occupancy carries a canonical Event UUID searchable on the Events page, linkable across workstations (honoring view access controls), printed in PDFs, and exportable/importable offline via single-code adaptive QR codes (camera scan or PNG/file import). Full-database event filters push CQL predicates — including **Adjudication Code** (`equals`, `does not equal`, `is any of`, `is empty`, `is not empty` across built-in Codes `1–11`, automated **`Code 9998: Extended Occupancy Gamma Alarm`**, automated **`Code 9999: EML Non-Threat`**, and site-configured custom disposition codes, backed by an asynchronous, idempotent startup backfill for historical adjudications) — directly to indexed PostgreSQL GIN and DuckDB Parquet queries, alarm priority sorts `Gamma-Neutron > Neutron > Gamma`, and National Statistics commands run sequentially with terminal observation binding.
- **Why it was implemented:** Operators in air-gapped or segmented secondary-inspection booths needed a zero-network way to hand off alarm traces and metadata to handheld devices or secondary workstations, while concurrent full-history statistics refreshes previously competed for CPU and memory on multi-month archives.
- **Read more:** [Operator Manual (English)](https://github.com/ORNL/osh-oakridge-modules/blob/main/services/sensorhub-service-oscar/src/main/resources/com/botts/impl/service/oscar/i18n/README.md).

### 2.7 Windows 11 Unattended Server Readiness, Modern Standby Fix, Pre-Login Docker & LAN/Tailscale TLS
- **What changed:** `configure-windows-host.ps1` (`.\oscar.bat prepare-host` / `.\oscar.bat host-check`) enforces 20 host-readiness checks on Windows 11: detects `S0 Low Power Idle` (Modern Standby) hardware via `powrprof.dll` and sets AC display timeout (`VIDEOIDLE`) to `0` (`Never`), registers `OSCAR-DockerDesktop-BootStart` (`AtStartup` `+10s`, `LogonType=S4U`) with an ACL-locked `%ProgramData%\OSCAR\start-docker-prelogin.ps1` helper so Docker Desktop and OSCAR start automatically after a power outage **before any user logs in**, caps WSL 2 memory/swap via `.wslconfig`, disables USB/NIC power saving, checks static vs. DHCP IPv4 stability, enables bugcheck auto-reboot, and auto-populates LAN IPv4 and Tailscale IPv4/IPv6/MagicDNS SANs into 10-year self-signed TLS certificates. Supported `stop`/`restart`/`upgrade` commands shut down `gateway -> oscar -> postgres` in strict dependency order.
- **Why it was implemented:** Live endurance testing on Windows 11 Modern Standby hardware revealed that Windows enters `S0 Low Power Idle` (`Kernel-Power 506`, dropping network and WSL 2 responsiveness) the moment the monitor blanks (`VIDEOIDLE > 0`), even when sleep timeout (`STANDBYIDLE`) is `0`, and that standard Windows startup tasks do not launch Docker Desktop after an unattended power-loss reboot until an interactive desktop login occurs. Unbounded WSL 2 page cache (`vmmemWSL`) could also starve the Windows host over multi-day runs.
- **Read more:** [Quick Start](../dist/release/QUICKSTART.md) and [Administrator Guide](../dist/release/DEPLOYMENT.md).

### 2.8 Admin-Uploaded External EML Runtime Plugin, Custom Alarm Assessment Developer API (`EmlAlarmAssessmentAlgorithm`) & Automatic `EML Non-Threat` Adjudication
- **What changed:** All non-redistributable EML JARs, models, and XML files have been removed from OSCAR repositories and release packages, replaced by a hot-loadable runtime plugin architecture (`EmlRuntimeRegistry`). Administrators upload their separately licensed LLNL EML `.jar` (or `.tar.gz`/`.zip` archive) or a custom alarm assessment algorithm plugin in **Services -> OSCAR Service -> EML Plugin Path** (`emlPluginPath`) — stored privately in `/var/lib/oscar/eml-plugin/` (`oscar_state`, included in backups and never exposed via HTTP buckets) and extracted to `/tmp/oscar-eml-runtime` — and enable `emlEnabled`, `isCollimated`, and `laneWidth` per Rapiscan lane. Developers can build custom alarm assessment plugins without any LLNL ERNIE XML/CSV files either as a zero-dependency standalone JDK JAR (`Oscar-Alarm-Assessment-Class` in `META-INF/MANIFEST.MF` implementing `Map<String, Object> evaluate(Map<String, Object> laneParams, List<String> dailyFileLines)`) or by implementing the typed `org.sensorhub.impl.utils.rad.eml.EmlAlarmAssessmentAlgorithm` interface registered in `META-INF/services/org.sensorhub.impl.utils.rad.eml.EmlAlarmAssessmentAlgorithm`. When EML or a custom assessment plugin evaluates an occupancy on `GX` as a verified `RELEASE` non-threat (without fallback or evaluation error), OSCAR suppresses the alarm from the Dashboard queue and browser notifications from initial publication and automatically records an `Adjudication` (`sender="EML"`, code `9999` **EML Non-Threat**, `secondaryInspectionStatus="NONE"`) with structured `EML_METADATA` JSON queryable in **Events** (`Adjudicated = EML Non-Threat` or `Adjudication Code = 9999: EML Non-Threat`) and rendered in **Event Details** (`EmlAnalysisCard` + `AdjudicationLog`) across `en`, `es`, `fr`, and `el`.
- **Why it was implemented:** EML source and model artifacts are owned and distributed separately outside ORNL's open-source repositories, while high-throughput VM-250 portals experience frequent benign NORM alarms that otherwise flood the central Dashboard queue if operators must manually clear every EML-released occupancy. Admin plugin upload cleanly separates third-party licensing from OSCAR releases while preserving 100% auditability and searchability for every auto-adjudicated non-threat event, and the `EmlAlarmAssessmentAlgorithm` / `Oscar-Alarm-Assessment-Class` developer SPI enables third-party researchers and integrators to deploy custom occupancy alarm assessment algorithms using only a standard JDK.
- **Read more:** [EML Integration & Custom Alarm Assessment Plugin Guide](EML_INTEGRATION.md) and [Administrator Guide](../dist/release/DEPLOYMENT.md).

### 2.9 Multi-Format Reports (`PDF`, `CSV`, `JSON`, `Excel`), Summed `All Selected Lanes` Adjudication Summary & In-UI Operator Help
- **What changed:** The Report Generator (`/report`) now supports five report types (`RDS Site Report`, `Lane Report`, `Event Report`, `Adjudication Report`, and `Adjudication Details`) across three scopes (`Entire Node`, `Operational View`, and `Specific Lanes`) and four export formats (`PDF`, `CSV`, `JSON`, and `Excel (.xlsx)`), always generating a fresh report and rendering an inline PDF or interactive tabular preview before download. The **Adjudication Report** (`ADJUDICATION`) starts with summed **All Selected Lanes** (`ALL_LANES`) `Disposition` and `Isotope Results` tables across all selected lanes before breaking down each individual lane. In addition, the OSCAR Viewer navigation bar now includes an in-UI **Operator Help & Glossary** (`?` icon) localized in English, Spanish, French, and Greek (`en`, `es`, `fr`, `el`), and all 24 SensorHub Admin configuration modules provide localized in-UI `README` tabs with plain-language term definitions.
- **Why it was implemented:** Site supervisors and auditors needed structured spreadsheet (`CSV`, `.xlsx`) and machine-readable (`JSON`) exports alongside concise, non-repetitive `PDF` summaries, with an immediate site/scope-wide adjudication roll-up at the top of the Adjudication Report before per-lane tables, plus self-contained plain-language help directly inside both web consoles for air-gapped operator workstations.
- **Read more:** [Operator Manual (English)](https://github.com/ORNL/osh-oakridge-modules/blob/main/services/sensorhub-service-oscar/src/main/resources/com/botts/impl/service/oscar/i18n/README.md) and [How-To Video Guides](VIDEO_GUIDES.md).

### 2.10 Lane-Level Extended Occupancy Fault (`Fault - Extended Occupancy`) & Automated `Code 9998: Extended Occupancy Gamma Alarm` Adjudication, Combined vs. Separate Accessibility Detector Plots, Customizable Dashboard Widgets & Instant HLS Startup
- **What changed:**
  - **Extended Occupancy Fault Behavior & `Code 9998: Extended Occupancy Gamma Alarm` Auto-Adjudication:** Administrators configure `extendedOccupancyThresholdMinutes` (`1`–`1440` minutes, default `1` minute) per lane in SensorHub Admin (**Lane Sensor System -> Extended Occupancy Threshold (min)**). While a vehicle occupies a Rapiscan, Aspect, or RS350 lane, `OccupancyWrapper` tracks elapsed occupancy duration via a deadline timer and incoming daily-file/status samples; as soon as the occupancy reaches or exceeds `extendedOccupancyThresholdMinutes`, `OccupancyStatusOutput` publishes a canonical `occupancyStatus` fault observation (`extendedOccupancyFault = true`, `alarmState = "Fault - Extended Occupancy"`), lighting the lane's **Extended Occupancy** indicator on the **Status of Health** page and Dashboard lane card and incrementing the `Ext-Occ` fault count in National Statistics and Lane Reports until the vehicle exits (`Clear`). When the extended occupancy completes, if it raised a **gamma-only alarm** (`gammaAlarm = true` and `neutronAlarm = false`), OSCAR automatically adjudicates the occupancy prior to publication: it stamps `"extended-occupancy-gamma"` and `"code:9998"` onto `occupancy.adjudicatedIds` at `t = 0` (suppressing the alarm from the live Dashboard queue and browser notifications without flashing, and superseding any pending EML release) and persists a durable `Adjudication` observation with disposition **`Code 9998: Extended Occupancy Gamma Alarm`** (`username = "AUTO"`, `secondaryInspectionStatus = "NONE"`). Any extended occupancy that includes a **neutron alarm** (`Gamma-Neutron` or `Neutron`) is **never** auto-adjudicated and remains a prominent active alarm requiring operator adjudication. Operators can filter and audit `Code 9998: Extended Occupancy Gamma Alarm` events on the **Events** page, inspect the automated disposition in **Event Details**, and review counts in **Adjudication Reports** and **Adjudication Details** alongside `Code 9999: EML Non-Threat`.
  - **Combined vs. Separate Accessibility Detector Plots, Customizable Dashboard & Instant HLS Startup:** In Lane View and Event Details, individual detector mode (`Show Individual Detectors`) now combines non-summed gamma detectors (`G1`–`G4+`) onto one multi-line chart and non-summed neutron detectors (`N1`–`N4+`) onto a second multi-line chart so operators can immediately see which detector has the highest count rate, with a persisted **Separate Plots (Accessibility)** toggle that splits each detector into its own chart for color-blind accessibility. Operators can also show/hide and reorder Dashboard widgets via **Customize Dashboard** (persisted per workstation/view and reclaiming layout space cleanly), and live HLS camera startup uses directory-scoped cleanup plus a bounded native keyframe-aligned GOP seed cache in `MpegTsProcessor` so physical and emulated cameras begin playing immediately without waiting for full-bucket scans or multiple future camera GOPs.
- **Why it was implemented:** Stationary vehicles holding a portal lane past the extended-occupancy threshold frequently trigger gamma alarms that would otherwise flood the active Dashboard queue; logging `Fault - Extended Occupancy` when the threshold is crossed and automatically dispositioning gamma-only extended occupancy alarms as **`Code 9998: Extended Occupancy Gamma Alarm`** (while never suppressing neutron alarms) keeps operator queues focused on actionable threats while preserving a complete, queryable audit trail. Operators also needed both direct per-detector radiation comparison on shared axes and color-blind-safe separate plots, command centers needed to tailor wallboard layouts by hiding unused dashboard sections, and physical IP cameras with multi-second keyframe intervals previously delayed live HLS playback if opened mid-GOP.

### 2.11 Parent-Only Operational Stream Purging, 24-Hour Transient Command Pruning, Append-Only Adjudication History & Zero-Allocation FFmpeg Demuxing
- **What changed:**
  - **Hourly `connectionStatus` & Routine `Clear` `occupancyStatus` Purging (`DatabasePurger` + `EMLContextualOutput`):** `EMLContextualOutput` and driver connection outputs now deduplicate identical `connectionStatus` emissions so observations are published only on state transitions. Every hour, `DatabasePurger` purges `connectionStatus` rows older than **1 hour** (always preserving the latest observation per datastream for instant `resultTime=latest` health queries) and purges routine `Clear` `occupancyStatus` heartbeat rows older than **1 hour** (preserving the latest row per datastream plus all non-`Clear` fault/alarm transitions).
  - **Fast-Path Parent-Table-Only (`ONLY oscar.obs`) Maintenance:** `OscarTieredObsStore` installs a dedicated partial index `obs_mutable_datastream_phenomenon_idx ON ONLY oscar.obs (datastreamid, phenomenontime ASC, id ASC) WHERE archivegenerationid IS NULL` (15th index on `oscar.obs`). When purging mutable streams (`connectionStatus`, `occupancyStatus`, `dailyFile`), `OscarTieredObsStore` queries and deletes exclusively from `ONLY oscar.obs` (`DELETE FROM ONLY obs WHERE id=ANY ($1::bigint[]) AND archivegenerationid IS NULL RETURNING id`), completely bypassing `osg_*` child partition scans, `oscar_obs_stage_owner` anti-joins, and PostgreSQL temporary file spills (`0` bytes of `temp_bytes` across 50-lane regression cycles).
  - **24-Hour Transient Command & Status Pruning (`cmd_commands` & `cmd_status`):** Every hour, `DatabasePurger.purgeOldCommands()` deletes transient operational commands (`streamControl`, `videoControl`, `ptzControl`, `hlsControl`, `oscarServiceControl`) older than **24 hours** along with their cascading `cmd_status` entries (`PostgisCommandStoreImpl` and `PostgisCommandStatusStore`), while permanently preserving all `%adjudicate%` and audit command streams.
  - **Append-Only Adjudication History, CQL2 JSONB `@>` Containment & Multi-Stream Viewer Discovery:** `AdjudicationControl` is strictly append-only — every operator or automated adjudication inserts a new `adjudication` observation and appends both its public encoded observation ID and `"code:<n>"` tag onto the parent `occupancy` observation's `adjudicatedIds` JSONB array without deleting or overwriting earlier decisions. `QueryBuilderObsStore` evaluates CQL2 `adjudicatedIds` equality predicates using PostgreSQL JSONB array containment (`@> to_jsonb($1::text)`), and the Viewer's `AdjudicationLog` discovers all adjudication datastreams on a lane and merges records matched by `adjudicatedIds` or `occupancyObsId`.
  - **Zero-Allocation Native FFmpeg `AVPacket` Reuse (`MpegTsProcessor` & `FileOutput`):** Camera demuxing loops allocate a single native `AVPacket` prior to the loop, call `av_packet_unref` at the end of every iteration, and yield `1 ms` on consecutive `EAGAIN` non-blocking polls instead of allocating and freeing a native `AVPacket` struct on every frame or spinning hot on empty sockets.
  - **Automatic Rapiscan Daily Setup Parameter Sync & Coalesced Non-Blocking `config.json` Persistence (`SetupGammaOutput`, `SetupNeutronOutput`, `RapiscanConfigSaver`):** When a Rapiscan RPM publishes its daily setup messages (`SG1`–`SG3` for all 16 gamma setup parameters and `SN1`–`SN2` for all 10 neutron setup parameters), OSCAR parses and compares the incoming hardware values against `RapiscanConfig` (`setupGammaConfig` and `setupNeutronConfig`), updates live `GammaThresholdOutput` (`nsigma` as a full `double` plus `bckgndcounttime1`) and `EMLService` calibration parameters in memory at `O(1)` cost, and schedules a debounced (`2 s`), coalesced background save (`RapiscanConfigSaver`) only when at least one parameter value actually changes. Even if all 50 Rapiscan lanes emit their daily setup blocks simultaneously at midnight, sensor TCP reader threads never touch disk I/O or lock contention, and `config.json` is flushed at most once on a single daemon thread.
- **Why it was implemented:** Even with detector counts tiered to Parquet, unpurged `connectionStatus` heartbeats, routine `Clear` `occupancyStatus` transitions, and frequent camera/HLS/statistics command records would slowly grow `ONLY oscar.obs` and `cmd_commands` over months of 50-lane operation, while scanning `obs` across attached `osg_*` partitions during hourly purges caused unnecessary query work. Scoping mutable purges to `ONLY oscar.obs` with a partial index and pruning transient operational status/commands keeps the PostgreSQL parent tables tiny while preserving 100% of evidentiary occupancies, append-only adjudication trails, and audit commands. Likewise, change-detected, coalesced background persistence for daily Rapiscan setup messages keeps `config.json` and live threshold/EML calculations synchronized with the physical RPM hardware without impacting real-time stream latency or disk I/O.

## 3. Multi-Year System Resources & Performance Comparison: Legacy `v3.9` vs. Current `v3.11.0` (50 Lanes, 2 Cameras/Lane — 100 Cameras Total)

To illustrate why the architectural improvements introduced since `v3.9` (`PARQUET_PRIMARY` 30-minute hot staging with ZSTD Parquet retirement, asynchronous 5-keyframe JPEG media decimation with 24-hour MP4 rollback grace, $O(1)$ retention cursor watermarks, `obs_datastreams` `fillfactor=70` HOT updates, loopback `MediaMTX` RTSP deduplication, shared HLS viewer leases, keyframe-seeded HLS startup, lazy `osh-js` stream connectors, and bounded 10,000-row client state) were necessary, the tables below compare a **50-lane site with 2 cameras per lane (100 cameras total)** running the legacy `v3.9` architecture against the current `v3.11.0` architecture across a **5-year deployment horizon**.

### 3.1 Workload Baseline (50 Lanes × 2 Cameras/Lane = 100 Cameras)

- **Radiation & Health Telemetry:** `50` RPM lanes + `100` camera drivers generating `~220–250 observations/sec` (`~20.0M observations/day`, `~7.3B observations/year`, `~36.5B observations over 5 years`) across `~1,059` active datastreams.
- **Occupancy & Alarm Video Workload:** `~100 occupancies/lane/day` (`5,000 occupancies/day` site-wide = `10,000 camera clips/day` across 100 cameras; `~5–10%` alarm rate = `500–1,000 alarm clips/day`).

### 3.2 Architectural & Resource Comparison by Subsystem (50 Lanes / 100 Cameras)

| Dimension | Legacy `v3.9` Setup (Pre-Parquet / Pre-Retention / Direct RTSP) | Current `v3.11.0` Setup (`PARQUET_PRIMARY` + Tiered Retention + `MediaMTX`) | Why the Change Was Necessary |
| :--- | :--- | :--- | :--- |
| **Observation Storage Engine** | Monolithic embedded H2 / unretired relational table storing every raw 1 Hz observation and index entry forever on hot disk. | **30-min `LOGGED` PostgreSQL hot staging** (`~41 min` max lifecycle) retired atomically every minute into **ZSTD-compressed columnar Parquet** files with SHA-256 manifest verification. | Under `v3.9`, B-tree index depth and MVStore write amplification grew with total historical rows, causing `~12–16 GiB/day` of DB growth and severe I/O stalls once the DB exceeded RAM. |
| **Hot Database Working Set** | Unbounded: `~450 GiB` at Month 1 → `~5.1 TiB` at Year 1 → **`~25.5 TiB` at Year 5** (`36.5B` live B-tree tuples). | **Permanently bounded at 1 open 30-min child (`~350K–500K` rows, `< 250 MiB` table data)** whether running for 1 hour or 5 years; logical PostgreSQL DB plateaus at **`~16–18 GiB`**. | Keeps hot B-tree indexes entirely in RAM (`80–100 MiB` PostgreSQL `anon` memory) forever so real-time ingestion and live queries never degrade over multi-year operation. |
| **Cold Telemetry Archive Size** | None (all data remained uncompressed in hot B-tree pages at `~5.1 TiB/year`). | **`~158 MiB/day` (`~56 GiB/year`, `~168 GiB` at Year 3, `~280 GiB` at Year 5)** in ZSTD columnar Parquet (**`~99%` hot-DB reduction, `>95%` total disk reduction**). | Enables multi-year on-box telemetry retention on standard 500 GB–1 TB SSDs without external SAN storage. |
| **Camera Media Storage (100 Cameras)** | All raw H.264 `.mp4` occupancy/alarm clips retained indefinitely on disk (`~20–35 GiB/day` across 100 cameras; **`~7.3–12.7 TiB/year`**) + full-bucket `Files.walk()` scans. | Alarm clips asynchronously decimated into **5 keyframe JPEGs** (`>90%` size reduction); raw `.mp4` files kept only for a **24h rollback window (`~8–11 GiB` flat plateau)**; $O(1)$ `RetentionCursor` + `15% / 8%` free-disk watermarks. | Without MP4 expiration and keyframe decimation, 100 cameras exhaust a 1 TB drive in **18–30 days**, crashing the server and corrupting the database. |
| **`obs_datastreams` Metadata Updates** | Every observation updated `resultTime` on `obs_datastreams`, generating millions of dead tuples/day and table bloat across 1,059 datastreams. | `fillfactor=70` + redundant `resultTime` update suppression yields **`94.2%–98.7%` PostgreSQL HOT-update ratio**; table stays **`~13–15 MiB`** permanently. | Eliminated autovacuum storms and metadata lock contention during 50-lane concurrent bursts. |
| **100-Camera RTSP & HLS Pipeline** | Each sensor/viewer opened direct RTSP sockets to cameras, ran unthrottled demux loops, walked the entire `videos` bucket on HLS start/stop, and leaked native FFmpeg `AVPacket`/`AVFrame` buffers on reconnects. | Loopback **`MediaMTX` sidecar** deduplicates upstream RTSP to **1 TCP connection per camera**, issues clean `RTSP TEARDOWN`, shares HLS across 64 viewers (`X-OSCAR-HLS-Viewer`), scopes HLS cleanup to the stream directory, seeds HLS startup from a bounded GOP cache, and frees all native packets deterministically. | Physical IP cameras (Axis/Reolink) drop connections when multiple direct RTSP sockets open, full-bucket walks caused `15–20s` command stalls, and native FFmpeg packet leaks previously caused container OOM kills. |
| **Server JVM Memory (`oscar` Container)** | Started at `~3.5 GiB`, climbed continuously via unbounded caches, large query result sets, and native FFmpeg leaks until **`OutOfMemoryError` (`>8–16 GiB`) within days/weeks**. | **Flat `1.53–1.78 GiB` anonymous heap** (`~2.0–3.2 GiB` total RSS) across 70+ hour soak tests; **`0` OOMs and `0` restarts** over multi-year projection. | Eliminates periodic server crashes, GC stop-the-world pauses, and manual container restarts. |
| **Operator Browser Memory (`oscar-viewer`)** | Eager `MqttTopicConnector` + `BroadcastChannel` creation per REST object + unbounded Redux `EventTableData[]` leaked **`~0.5–1.5 GiB/day`**, crashing 24/7 wallboards in **24–48 hours**. | Lazy `createLazyStreamConnector()`, reference-counted WebSocket leases (`acquireSharedConnection`), and bounded `MAX_CLIENT_EVENTS = 10,000` keep browser tab RAM flat at **`~180–260 MiB`**. | Allows 24/7 operator command-center wallboards to run continuously for months/years without browser tab crashes. |
| **Query & API Latency (50 Lanes)** | $O(N)$ `OFFSET/LIMIT` & B-tree scans degraded as table size grew: `~400 ms` (Day 1) → `~5–8 s` (Month 1) → **`>30–60 s` / HTTP 504 timeouts (Month 6 – Year 1+)**. | **$O(1)$ hot-partition lookup (`24–52 ms`)**, **50-lane burst (`345 ms` Ubuntu)**, and **date-pruned Parquet + $O(1)$ keyset cursor pagination (`67–153 ms` p95)** across multi-year history. | Prevents the operator UI, Event Table, and Report Generator from freezing or timing out as historical data accumulates over years. |
