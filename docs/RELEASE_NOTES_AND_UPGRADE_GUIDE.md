# OSCAR 3.11.9 (Amber) Release Overview, Architectural Rationale, and User Guide

OSCAR 3.11.9 (Amber) is engineered for continuous 24/7 operation across multi-year retention windows at large radiation portal monitoring (RPM) sites (up to 50 concurrent RPM and RTSP camera lanes per server) on Ubuntu Server 24.04 x86-64 and Windows 11 x86-64.

This guide summarizes everything changed from public `v3.8.0` through **OSCAR 3.11.9 (Amber)**, **why** each major architectural and operational change was implemented, which release artifact to download, and where **new users** and **existing users** should start.

---

### Path B — Current Users Running `pre-3.11.0` (`3.10.0`, `3.9.x`, `3.8.x`, or Earlier)

OSCAR 3.11.9 introduces a data-checksummed PostgreSQL 16 cluster, the `PARQUET_PRIMARY` tiered observation store, deployment-bound storage-root identity markers, and the direct daily-file journal. **To protect existing deployments from unexpected data mutations, `upgrade` never silently converts a `pre-3.11.0` database or overwrites a saved `config.json`.**

Choose one of two explicit rollout options depending on site requirements:

1. **Recommended for Full 3.11.9 Multi-Year Storage & Performance (`PARQUET_PRIMARY`):**
   - Preserve the existing `pre-3.11.0` deployment read-only after taking its supported backup/export.
   - Deploy OSCAR 3.11.9 into a clean directory and fresh storage roots using `oscar init` ([Quick Start](../dist/release/QUICKSTART.md)) so PostgreSQL initializes with `--data-checksums`, `PARQUET_PRIMARY` 30-minute stage partitions, the direct daily-file journal, and five-frame JPEG media retention.
   - Re-import your site's lane CSV (updated with optional `Views` column assignments; see [Operational Views](OPERATIONAL_VIEWS.md)), click **Apply** and **Save Configuration** in SensorHub Admin, and run a supported `oscar restart`. Migrate historical records separately only if site policy requires it.
2. **Retaining an Existing Legacy Volume Set In-Place (Without `PARQUET_PRIMARY` Re-Initialization):**
   - Read the **3.11.9 storage migration boundary** section of the [Administrator Guide](../dist/release/DEPLOYMENT.md) and **Existing pre-3.11.0 deployments** in [Storage Operations](STORAGE_OPERATIONS.md) before running any command.
   - Only after verifying that the existing named Docker volumes and any nonempty archive/backup directories belong to that exact deployment, use the explicit one-time adoption flags (`--adopt-legacy-volumes` / `-AdoptLegacyVolumes` and, when applicable, `--adopt-legacy-storage-roots` / `-AdoptLegacyStorageRoots`). Retain the resulting `.oscar-volume-adoption` receipt alongside `.env`, `secrets/`, and `tls/`.

### Path C — Current Users Upgrading an Existing `3.11.9+` Same-Profile Deployment

- **Option 1 — 1-Click Browser GUI System Update (No GitHub Login Required):** Sign in as an Administrator, open **`Users & Access` (`/users?tab=update`) -> `System Update`** (or click **Open System Update** inside **`Help (?)`**), click **Check GitHub for Updates** (or upload an offline `oscar-<version>.zip` on air-gapped portals), optionally check **Create an encrypted backup snapshot before upgrading**, and click **Download & Install**. The detached host `oscar-update` agent anonymously downloads and SHA-256-verifies the release archive, extracts into a clean sibling directory, copies `.env`, `secrets/`, `tls/`, and `.oscar-volume-adoption`, upgrades containers while preserving all PostgreSQL and Parquet data, and automatically rolls back if HTTPS readiness fails.
- **Option 2 — Manual / Automated Host CLI Upgrade:**
  1. Run `sudo bash oscar.sh update check` / `sudo bash oscar.sh update apply` (Ubuntu 24.04) or `.\oscar.bat update check` / `.\oscar.bat update apply` (Windows 11) — **or** perform the classic manual clean-directory upgrade below:
  2. If `OSCAR_BACKUP_MODE=single` is enabled, run and verify a fresh snapshot (`oscar backup` and `oscar backup-verify`; see [Backup and Restore](BACKUP_RESTORE.md)).
  3. Extract the new release ZIP into a **clean sibling directory** (never extract over an existing release folder).
  4. Copy **only** `.env`, `secrets/`, and `tls/` (plus `.oscar-volume-adoption` if previously created) from the prior release directory into the new directory.
  5. Run `.\oscar.bat upgrade` (Windows) or `sudo bash oscar.sh upgrade` (Ubuntu). Setup validates volume/root ownership, runs the idempotent offline daily-file index check under the storage lock, and force-recreates all containers while preserving `oscar_oscar_state`, `oscar_postgres_data`, and external archive/backup roots. See **Upgrade** in [Administrator Guide](../dist/release/DEPLOYMENT.md).

## 2. Major New Features and Why They Were Implemented

### 2.1 `PARQUET_PRIMARY` Tiered Observation Storage, Startup Route Reconciliation & DuckDB Query Federation
- **What changed:** Replacing the single unpartitioned, unretired PostgreSQL/PostGIS `obs` table architecture used in `v3.0.0`–`v3.10.0` (after OSCAR migrated off pre-`3.0` embedded H2 `MVObsSystemDatabase` in `3.0.0-alpha` / `3.0.0-alpha.1`), OSCAR 3.11.9 runs a containerized 3-service stack (`oscar-gateway` Nginx TLS reverse proxy, `oscar` Java 21 runtime, and `oscar-postgis` data-checksummed PostgreSQL 16/PostGIS). All **22** operational and evidentiary streams (`gammaCounts`, `gammaThreshold`, `neutronCounts`, `setupGamma`, `setupNeutron`, `speed`, `backgroundReport`, `foregroundReport`, `status`, `emlContextual`, `emlScanContextual`, `emlAnalysis`, `dailyFile`, `connectionStatus`, `occupancyStatus`, `tamper`, `occupancy`, `adjudication`, `report`, `siteStatistics`, `nationalSummary`, `vehicleOcr`) write into UTC-aligned 30-minute `LOGGED` PostgreSQL child partitions (`osg_*`). Once a 30-minute window closes (plus a 5-minute clock-skew/late-arrival safety delay), a background worker exports the window into Hive-partitioned (`date=YYYY-MM-DD/profile=RAW_GATED`), Zstandard-compressed Apache Parquet files, populates `oscar_obs_latest`, 22 per-generation summary counters on `oscar_archive_schema` (including per-category unadjudicated/adjudicated Gamma, Neutron, and Gamma-Neutron alarm counters, whole-generation `TimeContainedSummarySpec` time-bounded count pushdown, and persistent 4-byte `base_summary_mask` bitmasks on `oscar_obs_overlay` so cold 15-day multi-generation count summaries execute entirely in PostgreSQL without reading mutated Parquet files over `9p`), and `oscar_event_locator`, verifies exact row count, UUID digest, and SHA-256 parity, and retires the entire staging table in `O(1)` metadata time (`NO INHERIT` + `DROP TABLE`). Only static singleton configuration streams (`sensorLocation`, `adjudicationCodes`, `siteInfo`, ~52 rows total across 50 lanes) remain in `ONLY oscar.obs`. When an archived `occupancy` is adjudicated or re-adjudicated, `AdjudicationControl` appends a new `adjudication` observation (via non-blocking `submitCommandWithId` and indexed `cmd_status` lookup) and updates the archived `occupancy` in `oscar_obs_overlay` + `oscar_obs_latest` using content-addressed Schema v5 `oscar_obs_schema_catalog` (`schema_sha256` foreign key, `schema_json = NULL`) without rewriting Parquet, while `oscar_tombstone (obs_id, datastream_id)` scopes cold-row deletes per datastream (with automatic `resultTime=latest` live-row replacement in `oscar_obs_latest`) and `countObservationMutations(Set<Long> dataStreams)` scopes mutation checks to the queried datastreams and preserves bounded pagination (`saturateAdd(limit, mutationCount)`). Cold `CQL2` queries pre-compile AST matchers once per query (`JsonCqlEvaluator.compileMatcher`) and cache verified Parquet objects inside a disk-proportional (`2–8 GiB`, excluded from backups) native `ext4` cache (`/var/lib/oscar/.cache/oscar-9p-parquet-cache`) when running over Windows WSL 2 `drvfs`/`9p` mounts so multi-week archives avoid LRU thrashing while keeping `OSCAR_ARCHIVE_DIR` on a durable host bind mount. On startup, OSCAR automatically reconciles `oscar_obs_storage_route` entries (`reconcileRoutes()`) so any datastream matching the 22 allowlisted outputs is upgraded to `immutable=true`, reclaims empty expired `ATTACHED` and leftover `DETACHED` stage partitions (`reclaimEmptyOrRetiredStages()`), retroactively drains and compacts (`VACUUM (FULL, ANALYZE) ONLY obs`) any legacy unarchived rows sitting in `ONLY oscar.obs` into verified Parquet generations, and backfills summary counters and `oscar_obs_latest` for pre-upgrade generations. Embedded DuckDB transparently federates hot PostgreSQL stages and cold Parquet generations behind standard OpenSensorHub `IObsSystemDatabase` / OGC `ConSys` / CQL2 APIs.
- **Why it was implemented:** On a 50-lane site emitting continuous 1 Hz detector, status, and Enhanced Machine Learning (`EML`) telemetry plus thousands of occupancies, vehicle OCR reads, and adjudications per week, retaining any growing stream forever in an unpartitioned PostgreSQL `obs` table (`v3.0.0`–`v3.10.0`) or `ONLY oscar.obs` eventually bloats its parent B-tree/GIN indexes, amplifies WAL/autovacuum churn, and causes multi-year latency drift. Routing all 22 operational and evidentiary streams into 30-minute stage partitions and dropping whole partitions after Parquet parity keeps `ONLY oscar.obs` permanently near-empty (~52 static rows, ~200 KiB total with all 15 indexes), serves `resultTime=latest` queries in `< 0.5 ms` from `oscar_obs_latest`, evaluates `StatisticsOutput` and Dashboard/Event Log alarm & fault counts in `< 1 ms` from `oscar_archive_schema` summary counters, compresses cold history ~10–15x in self-describing Parquet, and preserves 100% OpenSensorHub API compatibility.
- **Read more:** [Storage Architecture](STORAGE_ARCHITECTURE.md), [Data Lifecycle Policy](DATA_LIFECYCLE.md), [Cold Archive Format](ARCHIVE_FORMAT.md), and [Storage Operations](STORAGE_OPERATIONS.md).

### 2.2 Exact-Five JPEG Retained Alarm Media & Bounded MP4 Lifecycle
- **What changed:** Completed alarm camera recordings are asynchronously decoded into five deterministic baseline sRGB JPEG keyframes (`FIRST`, `QUARTER`, `MIDDLE`, `THREE_QUARTERS`, `LAST`) verified by a manifest commit marker, with bounded post-roll so even 1-second occupancies capture five frames. Source MP4 clips remain playable during a 24-hour post-publication rollback grace before automatic reclamation (failed or `<5`-frame clips preserve their MP4 indefinitely), and after 30 days secondary frames prune while `MIDDLE` (`frame-03.jpg`) stays online for multi-year event history. The Viewer renders an interactive 5-frame gallery with automatic legacy MP4 fallback.
- **Why it was implemented:** Retaining raw H.264 MP4 video for thousands of alarms across 50 cameras quickly exhausts terabytes of storage, while frame-dropping video re-transcoding was CPU-heavy and fragile on short clips. Extracting five verified JPEGs immediately preserves evidentiary visual context across the entire occupancy trajectory at a tiny fraction of MP4 disk cost, and pruning down to the middle frame after 30 days bounds multi-year media growth predictably.
- **Read more:** [Retained Media v1 Specification](https://github.com/ORNL/osh-oakridge-modules/blob/main/docs/retained-media-v1.md), [Live Video & Recording Guide](LIVE_VIDEO.md), and [Data Lifecycle Policy](DATA_LIFECYCLE.md).

### 2.3 Crash-Recoverable Direct Daily-File Journal (`DailyFileJournalService`)
- **What changed:** Rapiscan, RS350, and Aspect drivers append raw detector records before parsing into a per-lane, length-prefixed, `CRC32C`-verified write-ahead journal on disk, decoupled from historical backlog rendering, with atomic daily CSV + SHA-256 manifest publication, 30-day replay-verified journal cleanup, and live Viewer display of the latest 15 daily-file messages.
- **Why it was implemented:** Legacy daily-file generation reconstructed CSVs from parsed database observations or in-memory buffers, meaning a restart, parser error, or database stall could drop raw vendor messages or cause multi-minute startup spikes across 50 lanes. Direct pre-parse journaling guarantees source-message durability and fast bounded restarts.
- **Read more:** [Daily-File Journal v1 Specification](https://github.com/ORNL/osh-oakridge-modules/blob/main/docs/daily-file-journal-v1.md) and [Storage Architecture](STORAGE_ARCHITECTURE.md).

### 2.4 Zero-Downtime Continual & Occasional USB NVMe Incremental Backups (`/usb-backups`), Bare-Metal Provisioning, Single-Snapshot Backup & Legal Holds
- **What changed:** Fresh deployments default to `OSCAR_BACKUP_MODE=disabled` with `archive_mode=off` (no continuous external WAL archive mount) and support two complementary recovery architectures: **(a)** zero-downtime (`0.0 s` portal outage, `Nice=19` / `IOSchedulingClass=idle` / `--cpus=1`) **Continual & Occasional USB NVMe Incremental Backups** managed from **`OSCAR Viewer -> USB Backups` (`/usb-backups`)** (`UsbBackupControlBridge` + host `oscar-usb-backup-agent` with zero `docker.sock` exposure) or `oscar.sh` / `oscar.bat usb-backup`, writing `O(1)` sealed daily `.tar` packs (`~1.03x` disk overhead across multi-hundred-gigabyte archives), supporting live `continual` <-> `occasional` <-> `disabled` switching, safe `eject` (`SAFE_TO_UNPLUG`) with cross-platform `NTFS` field-laptop delta offload (`COPY-TO-ANOTHER-DRIVE.bat` / `copy-to-another-drive.sh`), automatic reconnect catch-up, USB-to-NVMe enclosure Bulk-Only/No-LPM quirk hardening, 1-click `oscar-backup-key.txt` escrow download, and 1-command bare-metal recovery via `usb-backup restore` or the Ubuntu 24.04 autoinstall USB + First-Boot Recovery Wizard (`create-autoinstall-usb` + `oscar-wizard`); and **(b)** opt-in `single` mode on a non-overlapping backup path (`oscar upgrade --backup-mode single --backup-dir ...`), producing an HMAC-SHA-256-verified, `pg_verifybackup`-checked recovery point combining a streamed PostgreSQL base backup (`--wal-method=stream`), OSCAR state, Parquet cold-tier inventory, and AES-256-CBC encrypted credentials behind an atomic `CURRENT` pointer. Observation and generation legal holds (`GENERATION_EXACT`, `HOT_EXACT`, `COLD_RANGE_CONSERVATIVE`) and two-step tokenized cold-archive purges protect evidentiary records across API/UI and CLI operations.
- **Why it was implemented:** Continuous external PostgreSQL WAL archiving on unattended edge servers created silent disk-exhaustion hazards whenever backup media disconnected or filled up, while multi-snapshot local retention multiplied multi-gigabyte cold-archive footprints and remote field sites needed a zero-downtime external USB 3.x NVMe rotation workflow operable without Linux/PowerShell CLI expertise.
- **Read more:** [Continual & Occasional USB NVMe Incremental Backup Guide](CONTINUAL_AND_USB_BACKUP_GUIDE.md), [Ubuntu 24.04 Field Setup & Bare-Metal Guide](UBUNTU_FIELD_SETUP_GUIDE.md), [Backup, Restore, and Recovery Runbook](BACKUP_RESTORE.md), and [Storage Operations](STORAGE_OPERATIONS.md).

### 2.5 Scoped Operational Views Dropdown, Explicit Result-Horizon Notices, Automatic Tight Lane-Extent Map Zoom, Status of Health & Loopback RTSP/HLS Video Resilience
- **What changed:** Administrators can assign lanes to named workstation views (via Admin UI or CSV `OperationalViews` column) accessed at `/view/<slug>` or switched directly from the top-bar **Scoped View** dropdown (`All Lanes` + configured views with lane counts for unrestricted users, or strictly permitted `allowedViews` without `All Lanes` for gate-scoped operators), scoping live subscriptions, maps, event tables, statistics, health indicators, and reports. Across capped or time-windowed surfaces — including `24h / 7d / 15d` Lane View fault history, `200`-per-server Vehicle ID search (`16` most recent overlaid traces/thumbnails), `30`-day Event Details related-crossings banner, `1,000`-line Daily File slices, `15`-line live RPM message feed, `100`-row / `9`-column in-app report previews, `25`-bookmark Saved Queries limit, and `1,500`-sample extended-occupancy charts — OSCAR displays explicit non-intrusive scope/truncation notices while keeping `15m / 1h / 24h / 15d` temporal window presets directly in the Dashboard toolbar (and bounds historical Vehicle OCR and WebID time-window queries so older pages never drop records behind newer stream activity). The Dashboard, Map, and Operational View maps automatically zoom tightly to the bounding extent of the active lane markers (`zoomSnap: 0`, `padding: [14, 14]`, immediate `laneSystem` coordinate seeding, and `(0, 0)` Null Island exclusion) so all 4, 25, or 50 configured lanes are clearly visible without overlap or excess padding. A dedicated Status of Health page and compact Dashboard lane pills report independent RPM and camera connectivity, gamma/neutron faults, tamper state, and extended occupancy in bounded 30-second batches. For `rtsp://` and `rtsps://` cameras, OSCAR now embeds and supervises a transparent loopback `mediamtx` RTSP proxy inside the `oscar` container (`127.0.0.1`, keeping real camera URLs unchanged across `config.json`, Admin UI, and CSV imports/exports), deduplicating identical streams to a single upstream TCP camera socket per server, normalizing leading `//` stream paths, verifying upstream readiness and resetting `FFMPEGSensor`'s heartbeat state upon reconnect so `connectionStatus` reports `Online` immediately rather than waiting up to 15 minutes, reconnecting dropped streams in-place without restarting the SensorHub module, normalizing packet DTS/PTS discontinuities, and coordinating multi-operator shared live HLS leases with keyframe-gated startup. Empirical baseline hardware sizing, OCR camera resolution guidance, and `5`-lane vs. `50`-lane multi-year projections (`720p`/`1080p`, frame rate, GOP, hybrid OCR, and Ubuntu 24.04 vs. Windows 11 WSL 2) are documented in [`dist/release/DEPLOYMENT.md`](../dist/release/DEPLOYMENT.md#recommended-hardware-and-capacity-sizing).
- **Why it was implemented:** Large ports and facilities divide 50+ lanes across gate-specific operator consoles (`east-gate`, `west-gate`, `pedestrian`, etc.); opening unfiltered real-time MQTT/video feeds for every lane on every workstation wasted browser memory and distracted operators. Physical edge IP cameras also tightly cap concurrent TCP `:554` sessions and emit packet timestamp discontinuities or reject duplicate/malformed RTSP paths, while multiple operators viewing the same lane previously risked stopping each other's shared HLS stream on navigation.
- **Read more:** [Operational Views Guide](OPERATIONAL_VIEWS.md), [Status of Health Guide](STATUS_OF_HEALTH.md), and [Live Video Guide](LIVE_VIDEO.md).

### 2.6 Event UUID Direct Links, Full-Database Adjudication Code Filtering, QR Alarm Transfer & Serialized National Statistics
- **What changed:** Every occupancy carries a canonical Event UUID searchable on the Events page, linkable across workstations (honoring view access controls), printed in PDFs, and exportable/importable offline via single-code adaptive QR codes (camera scan or PNG/file import). Full-database event filters push CQL predicates — including **Adjudication Code** (`equals`, `does not equal`, `is any of`, `is empty`, `is not empty` across built-in Codes `1–11`, automated **`Code 9998: Extended Occupancy Gamma Alarm`**, automated **`Code 9999: EML Non-Threat`**, and site-configured custom disposition codes, backed by an asynchronous, idempotent startup backfill for historical adjudications) — directly to indexed PostgreSQL GIN and DuckDB Parquet queries, alarm priority sorts `Gamma-Neutron > Neutron > Gamma`, and National Statistics commands run sequentially with terminal observation binding.
- **Why it was implemented:** Operators in air-gapped or segmented secondary-inspection booths needed a zero-network way to hand off alarm traces and metadata to handheld devices or secondary workstations, while concurrent full-history statistics refreshes previously competed for CPU and memory on multi-month archives.
- **Read more:** [Operator Manual (English)](https://github.com/ORNL/osh-oakridge-modules/blob/main/services/sensorhub-service-oscar/src/main/resources/com/botts/impl/service/oscar/i18n/README.md).

### 2.7 Windows 11 Unattended Server Readiness, Modern Standby Fix, Pre-Login Docker & LAN/Tailscale TLS
- **What changed:** `configure-windows-host.ps1` (`.\oscar.bat prepare-host` / `.\oscar.bat host-check`) enforces 21 host-readiness checks on Windows 11: detects `S0 Low Power Idle` (Modern Standby) hardware via `powrprof.dll` and sets AC display timeout (`VIDEOIDLE`) to `0` (`Never`), configures low-latency AC-only processor scheduling (`PROCTHROTTLEMIN/MAX=100%`, `PERFEPP=0` Maximum Performance, and boost enabled while leaving DC battery profiles untouched), registers `OSCAR-DockerDesktop-BootStart` (`AtStartup` `+10s`, `LogonType=S4U`) with an ACL-locked `%ProgramData%\OSCAR\start-docker-prelogin.ps1` helper so Docker Desktop and OSCAR start automatically after a power outage **before any user logs in**, caps WSL 2 memory/swap via `.wslconfig` (with opt-in `-WslNetworkingMode mirrored` support), disables USB/NIC power saving, checks static vs. DHCP IPv4 stability, enables bugcheck auto-reboot, and auto-populates LAN IPv4 and Tailscale IPv4/IPv6/MagicDNS SANs into 10-year self-signed TLS certificates. Supported `stop`/`restart`/`upgrade` commands shut down `gateway -> oscar -> postgres` in strict dependency order.
- **Why it was implemented:** Live endurance testing on Windows 11 Modern Standby hardware revealed that Windows enters `S0 Low Power Idle` (`Kernel-Power 506`, dropping network and WSL 2 responsiveness) the moment the monitor blanks (`VIDEOIDLE > 0`), even when sleep timeout (`STANDBYIDLE`) is `0`, and that standard Windows startup tasks do not launch Docker Desktop after an unattended power-loss reboot until an interactive desktop login occurs. Unbounded WSL 2 page cache (`vmmemWSL`) could also starve the Windows host over multi-day runs.
- **Read more:** [Quick Start](../dist/release/QUICKSTART.md) and [Administrator Guide](../dist/release/DEPLOYMENT.md).

### 2.8 Admin-Uploaded External EML Runtime Plugin, Custom Alarm Assessment Developer API (`EmlAlarmAssessmentAlgorithm`) & Automatic `EML Non-Threat` Adjudication
- **What changed:** All non-redistributable EML JARs, models, and XML files have been removed from OSCAR repositories and release packages, replaced by a hot-loadable runtime plugin architecture (`EmlRuntimeRegistry`). Administrators upload their separately licensed LLNL EML `.jar` (or `.tar.gz`/`.zip` archive) or a custom alarm assessment algorithm plugin in **Services -> OSCAR Service -> EML Plugin Path** (`emlPluginPath`) — stored privately in `/var/lib/oscar/eml-plugin/` (`oscar_state`, included in backups and never exposed via HTTP buckets) and extracted to `/tmp/oscar-eml-runtime` — and enable `emlEnabled`, `isCollimated`, and `laneWidth` per Rapiscan lane. Developers can build custom alarm assessment plugins without any LLNL ERNIE XML/CSV files either as a zero-dependency standalone JDK JAR (`Oscar-Alarm-Assessment-Class` in `META-INF/MANIFEST.MF` implementing `Map<String, Object> evaluate(Map<String, Object> laneParams, List<String> dailyFileLines)`) or by implementing the typed `org.sensorhub.impl.utils.rad.eml.EmlAlarmAssessmentAlgorithm` interface registered in `META-INF/services/org.sensorhub.impl.utils.rad.eml.EmlAlarmAssessmentAlgorithm`. When EML or a custom assessment plugin evaluates an occupancy on `GX` as a verified `RELEASE` non-threat (without fallback or evaluation error), OSCAR suppresses the alarm from the Dashboard queue and browser notifications from initial publication and automatically records an `Adjudication` (`sender="EML"`, code `9999` **EML Non-Threat**, `secondaryInspectionStatus="NONE"`) with structured `EML_METADATA` JSON queryable in **Events** (`Adjudicated = EML Non-Threat` or `Adjudication Code = 9999: EML Non-Threat`) and rendered in **Event Details** (`EmlAnalysisCard` + `AdjudicationLog`) across `en`, `es`, `fr`, and `el`.
- **Why it was implemented:** EML source and model artifacts are owned and distributed separately outside ORNL's open-source repositories, while high-throughput VM-250 portals experience frequent benign NORM alarms that otherwise flood the central Dashboard queue if operators must manually clear every EML-released occupancy. Admin plugin upload cleanly separates third-party licensing from OSCAR releases while preserving 100% auditability and searchability for every auto-adjudicated non-threat event, and the `EmlAlarmAssessmentAlgorithm` / `Oscar-Alarm-Assessment-Class` developer SPI enables third-party researchers and integrators to deploy custom occupancy alarm assessment algorithms using only a standard JDK.
- **Read more:** [EML Integration & Custom Alarm Assessment Plugin Guide](EML_INTEGRATION.md) and [Administrator Guide](../dist/release/DEPLOYMENT.md).

### 2.9 Multi-Format Reports (`PDF`, `CSV`, `JSON`, `Excel`), Multi-Format Secondary Spectroscopy & Log-by-Default Spectrograms, UpSet Co-Occurrence Analytics, Consolidated `Vehicle Incident Report` (`VEHICLE_INCIDENT`), Multi-Pass Vehicle ID Search & Comparison, Bundled Offline Video Help & Redacted Support Bundle Export
- **What changed:** The Report Generator (`/report`) now supports six report types (`RDS Site Report`, `Lane Report`, `Event Report`, `Adjudication Report`, `Adjudication Details`, and `Vehicle Incident Report` / `VEHICLE_INCIDENT`) across three scopes (`Entire Node`, `Operational View`, and `Specific Lanes`) and four export formats (`PDF`, `CSV`, `JSON`, and `Excel (.xlsx)`), always generating a fresh report and rendering an inline PDF or interactive tabular preview before download. The **Adjudication Report** (`ADJUDICATION`) starts with summed **All Selected Lanes** (`ALL_LANES`) `Disposition` and `Isotope Results` tables across all selected lanes before breaking down each individual lane, while **Event**, **Adjudication**, and **Vehicle Incident** PDF & JSON reports plus the **Event Log** include **UpSet** co-occurrence intersection analytics across alarm categories, isotopes, and pass dispositions (listing populated main categories first ahead of zero-count categories, providing selectable main-category filter buttons alongside combination bars in OSCAR Viewer, and rolling any rare `SNM` intersections beyond the top 18 columns into a crimson **`Other SNM`** column so vertical SNM bars always equal the exact `SNM` set total). ### 2.10 Lane-Level Extended Occupancy Fault (`Fault - Extended Occupancy`) & Automated `Code 9998: Extended Occupancy Gamma Alarm` Adjudication, Site-Shared Per-Lane Dashboard Alarm Read/Acknowledge & Latching Audio, Combined vs. Separate Accessibility Detector Plots, Customizable Dashboard Widgets & Instant HLS Startup
- **What changed:**
  - **Extended Occupancy Fault Behavior & `Code 9998: Extended Occupancy Gamma Alarm` Auto-Adjudication:** Administrators configure `extendedOccupancyThresholdMinutes` (`1`–`1440` minutes, default `1` minute) per lane in SensorHub Admin (**Lane Sensor System -> Extended Occupancy Threshold (min)**). While a vehicle occupies a Rapiscan, Aspect, or RS350 lane, `OccupancyWrapper` tracks elapsed occupancy duration via a deadline timer and incoming daily-file/status samples; as soon as the occupancy reaches or exceeds `extendedOccupancyThresholdMinutes`, `OccupancyStatusOutput` publishes a canonical `occupancyStatus` fault observation (`extendedOccupancyFault = true`, `alarmState = "Fault - Extended Occupancy"`), lighting the lane's **Extended Occupancy** indicator on the **Status of Health** page and Dashboard lane card and incrementing the `Ext-Occ` fault count in National Statistics and Lane Reports until the vehicle exits (`Clear`). When the extended occupancy completes, if it raised a **gamma-only alarm** (`gammaAlarm = true` and `neutronAlarm = false`), OSCAR automatically adjudicates the occupancy prior to publication: it stamps `"extended-occupancy-gamma"` and `"code:9998"` onto `occupancy.adjudicatedIds` at `t = 0` (suppressing the alarm from the live Dashboard queue and browser notifications without flashing, and superseding any pending EML release) and persists a durable `Adjudication` observation with disposition **`Code 9998: Extended Occupancy Gamma Alarm`** (`username = "AUTO"`, `secondaryInspectionStatus = "NONE"`). Any extended occupancy that includes a **neutron alarm** (`Gamma-Neutron` or `Neutron`) is **never** auto-adjudicated and remains a prominent active alarm requiring operator adjudication. Operators can filter and audit `Code 9998: Extended Occupancy Gamma Alarm` events on the **Events** page, inspect the automated disposition in **Event Details**, and review counts in **Adjudication Reports** and **Adjudication Details** alongside `Code 9999: EML Non-Threat`.

  - **Combined vs. Separate Accessibility Detector Plots, Customizable Dashboard, Instant HLS Startup & Optional Asynchronous Per-Lane Container/Plate OCR:** In Lane View and Event Details, individual detector mode (`Show Individual Detectors`) now combines non-summed gamma detectors (`G1`–`G4+`) onto one multi-line chart and non-summed neutron detectors (`N1`–`N4+`) onto a second multi-line chart so operators can immediately see which detector has the highest count rate, with a persisted **Separate Plots (Accessibility)** toggle that splits each detector into its own chart for color-blind accessibility. Operators can also show/hide and reorder Dashboard widgets via **Customize Dashboard** (persisted per workstation/view and reclaiming layout space cleanly), and live HLS camera startup uses directory-scoped cleanup plus a bounded native keyframe-aligned GOP seed cache in `MpegTsProcessor` so physical and emulated cameras begin playing immediately without waiting for full-bucket scans or multiple future camera GOPs. ### 2.11 Parent-Only Operational Stream Purging, 24-Hour Transient Command Pruning, Append-Only Adjudication History & Zero-Allocation FFmpeg Demuxing
- **What changed:**
  - **Hourly `connectionStatus` & Routine `Clear` `occupancyStatus` Purging (`DatabasePurger` + `EMLContextualOutput`):** `EMLContextualOutput` and driver connection outputs now deduplicate identical `connectionStatus` emissions so observations are published only on state transitions. Every hour, `DatabasePurger` purges `connectionStatus` rows older than **1 hour** (always preserving the latest observation per datastream for instant `resultTime=latest` health queries) and purges routine `Clear` `occupancyStatus` heartbeat rows older than **1 hour** (preserving the latest row per datastream plus all non-`Clear` fault/alarm transitions).
  - **Fast-Path Parent-Table-Only (`ONLY oscar.obs`) Maintenance:** `OscarTieredObsStore` installs a dedicated partial index `obs_mutable_datastream_phenomenon_idx ON ONLY oscar.obs (datastreamid, phenomenontime ASC, id ASC) WHERE archivegenerationid IS NULL` (15th index on `oscar.obs`). When purging mutable streams (`connectionStatus`, `occupancyStatus`, `dailyFile`), `OscarTieredObsStore` queries and deletes exclusively from `ONLY oscar.obs` (`DELETE FROM ONLY obs WHERE id=ANY ($1::bigint[]) AND archivegenerationid IS NULL RETURNING id`), completely bypassing `osg_*` child partition scans, `oscar_obs_stage_owner` anti-joins, and PostgreSQL temporary file spills (`0` bytes of `temp_bytes` across 50-lane regression cycles).
  - **24-Hour Transient Command & Status Pruning (`cmd_commands` & `cmd_status`):** Every hour, `DatabasePurger.purgeOldCommands()` deletes transient operational commands (`streamControl`, `videoControl`, `ptzControl`, `hlsControl`, `oscarServiceControl`) older than **24 hours** along with their cascading `cmd_status` entries (`PostgisCommandStoreImpl` and `PostgisCommandStatusStore`), while permanently preserving all `%adjudicate%` and audit command streams.
  - **Append-Only Adjudication History, CQL2 JSONB `@>` Containment & Multi-Stream Viewer Discovery:** `AdjudicationControl` is strictly append-only — every operator or automated adjudication inserts a new `adjudication` observation and appends both its public encoded observation ID and `"code:<n>"` tag onto the parent `occupancy` observation's `adjudicatedIds` JSONB array without deleting or overwriting earlier decisions. `QueryBuilderObsStore` evaluates CQL2 `adjudicatedIds` equality predicates using PostgreSQL JSONB array containment (`@> to_jsonb($1::text)`), and the Viewer's `AdjudicationLog` discovers all adjudication datastreams on a lane and merges records matched by `adjudicatedIds` or `occupancyObsId`.
  - **Zero-Allocation Native FFmpeg `AVPacket` Reuse (`MpegTsProcessor` & `FileOutput`):** Camera demuxing loops allocate a single native `AVPacket` prior to the loop, call `av_packet_unref` at the end of every iteration, and yield `1 ms` on consecutive `EAGAIN` non-blocking polls instead of allocating and freeing a native `AVPacket` struct on every frame or spinning hot on empty sockets.
  - **Automatic Rapiscan Daily Setup Parameter Sync & Coalesced Non-Blocking `config.json` Persistence (`SetupGammaOutput`, `SetupNeutronOutput`, `RapiscanConfigSaver`):** When a Rapiscan RPM publishes its daily setup messages (`SG1`–`SG3` for all 16 gamma setup parameters and `SN1`–`SN2` for all 10 neutron setup parameters), OSCAR parses and compares the incoming hardware values against `RapiscanConfig` (`setupGammaConfig` and `setupNeutronConfig`), updates live `GammaThresholdOutput` (`nsigma` as a full `double` plus `bckgndcounttime1`) and `EMLService` calibration parameters in memory at `O(1)` cost, and schedules a debounced (`2 s`), coalesced background save (`RapiscanConfigSaver`) only when at least one parameter value actually changes. Even if all 50 Rapiscan lanes emit their daily setup blocks simultaneously at midnight, sensor TCP reader threads never touch disk I/O or lock contention, and `config.json` is flushed at most once on a single daemon thread.
- **Why it was implemented:** Even with detector counts tiered to Parquet, unpurged `connectionStatus` heartbeats, routine `Clear` `occupancyStatus` transitions, and frequent camera/HLS/statistics command records would slowly grow `ONLY oscar.obs` and `cmd_commands` over months of 50-lane operation, while scanning `obs` across attached `osg_*` partitions during hourly purges caused unnecessary query work. Scoping mutable purges to `ONLY oscar.obs` with a partial index and pruning transient operational status/commands keeps the PostgreSQL parent tables tiny while preserving 100% of evidentiary occupancies, append-only adjudication trails, and audit commands. Likewise, change-detected, coalesced background persistence for daily Rapiscan setup messages keeps `config.json` and live threshold/EML calculations synchronized with the physical RPM hardware without impacting real-time stream latency or disk I/O.

### 3.1 Baseline Reference Hardware, Recommended OCR Camera Profile & Two Reference Workloads

Because Tier-0 (`stencil_det_fp32.onnx`) detects oriented ROIs at `640×384` and then crops and `AffineTransform`-deskews directly from the **native camera frame** before `48px` CTC / INT8 `32×128` `PARSeq` recognition (while Tier-2 DBNet caps full-frame scans at `1600px`), `1080p @ 15 fps` preserves full optical check-digit sharpness without the `2×`–`4×` bandwidth, MP4 grace, and JPEG-decode overhead of `30 fps` or `4K`.
  - **Situational Overview Camera (`1×` per lane, non-OCR):** **`1280×720` (`720p`) @ `15 fps`, H.264, `1–2 s` closed GOP**, `~1.0–2.0 Mbps`. Pairing `1× 1080p @ 15 fps` + `1× 720p @ 15 fps` per lane holds aggregate RTSP ingress to **`~18–30 Mbps` on a 5-lane site** and **`~175–300 Mbps` on a 50-lane site** (`< 30%` of `1 GbE`), with a measured average retained JPEG size of **`~88–100 KiB/frame`**.
- **Reference Traffic & OCR Workload (`100` Occupancies/Lane/Day, `5%–10%` Alarm Rate):**
  - **Type A (`5` Lanes / `10` Cameras):** `~22–25 observations/sec` (`~2.0M/day`, `~0.73B/year`) across `~115` datastreams; `500 occupancies/day` (`25–50` alarm occupancies = `50–100` alarm camera clips/day).
  - **Type B (`50` Lanes / `100` Cameras):** `~220–250 observations/sec` (`~20.0M/day`, `~7.3B/year`, `~73.0B` over 10 years) across `~1,110` datastreams; `5,000 occupancies/day` (`250–500` alarm occupancies = `500–1,000` alarm camera clips/day).
  - **Hybrid Vehicle OCR (`sensorhub-process-ocr`):** `vehicleOcr` (`~422 B` JSONB staged → `~65 B` ZSTD Parquet row) adds `< 0.02 GiB/year` (`5` lanes) to `< 0.12 GiB/year` (`50` lanes) in recommended `alarmsOnly=true` mode (`< 1.2 GiB/year` across `50` lanes in `alarmsOnly=false` continual mode), while date-partitioned `files/ocr/crops/<YYYY-MM-DD>/` (`~2.3–2.7 KiB/crop`, `ocrCropRetentionDays = 365` default) stabilizes at **`~0.05 GiB` (`5` lanes) / `~0.5 GiB` (`50` lanes)** (`~7.5 GiB` if `alarmsOnly=false` on `50` lanes).

### 3.2 Architectural & Resource Comparison by Subsystem (`Legacy v3.8.0 / v3.9` vs. `Current v3.11.9`)

| Dimension | Legacy `v3.8.0` / `v3.9` Setup (Pre-Parquet / Pre-Retention / Direct RTSP) | Current `v3.11.9` Setup (`PARQUET_PRIMARY` + Tiered Retention + `MediaMTX` + Hybrid OCR) | Why the Change Was Necessary |
| :--- | :--- | :--- | :--- |
| **Observation Storage Engine** | Single unpartitioned, unretired PostgreSQL/PostGIS `obs` table storing every raw 1 Hz JSONB observation and index entry forever on hot disk. | **30-min `LOGGED` PostgreSQL hot staging** (`~41 min` nominal retirement budget) across all 22 operational/evidentiary streams, retired atomically into **ZSTD-compressed columnar Parquet** with row/UUID/SHA-256 parity verification. | Under `v3.8.0`/`v3.9`, PostgreSQL B-tree/GIN index depth, JSONB/TOAST page bloat, and autovacuum/WAL write amplification grew with total historical rows, causing `~14 GiB/day` of 50-lane DB growth and severe I/O stalls once indexes exceeded RAM. |
| **Hot PostgreSQL Working Set** | Unbounded (50 lanes): `~420 GiB` at Month 1 → `~5.1 TiB` at Year 1 → **`~25.5 TiB` at Year 5** (`36.5B` live B-tree tuples). | **Permanently bounded at `1` open 30-min child (`< 250 MiB` hot table data):** 7-day live telemetry confirms logical DB holds at **`~0.35 GiB` (`5` lanes) / `0.63 GiB` (`50` lanes)** and physical PostgreSQL + WAL volume stabilizes at **`~0.8 GiB` (`5` lanes) / `1.2–2.0 GiB` (`50` lanes)** across a 10-year lifecycle. | Keeps hot B-tree indexes entirely in RAM (`< 200 MiB` index footprint) forever so real-time ingestion and live queries never degrade over multi-year operation. |
| **Cold Telemetry Archive Size** | None (all data remained uncompressed in hot B-tree pages at `~5.1 TiB/year` on 50 lanes). | Empirically measured **`125.7 MiB/day` (`44.8 GiB/year`; `~45–50 GiB/yr` planning allowance) for 50 lanes** and **`~4.5–5.0 GiB/year` for 5 lanes** in ZSTD Parquet (**`>99%` hot-DB reduction**), plus `~0.35 GiB/yr` (`5` lanes) / `~3.5 GiB/yr` (`50` lanes) of immutable Daily-File CSVs. | Enables 10-year on-box telemetry retention on standard `1–2 TB` NVMe SSDs without external SAN storage. |
| **Camera Media Storage (`1080p` OCR + `720p` Overview)** | All raw H.264 `.mp4` clips retained indefinitely (`~20–35 GiB/day` across 100 cameras; **`~7.3–12.7 TiB/year`**) + full-bucket `Files.walk()` scans. | Alarm clips asynchronously decoded into **5 sRGB JPEGs** (`~88–100 KiB/frame`); source `.mp4` kept only for a **24h rollback grace (`~0.5 GiB` for 5L / `~4.5 GiB` for 50L)**; after `secondaryFrameRetentionDays = 30`, **4 of 5 JPEGs (`80%`) are pruned**, leaving only `frame-03.jpg` (`~1.8–3.6 GiB/yr` for 5L; `~18–36 GiB/yr` for 50L) backed by $O(1)$ `RetentionCursor` + `85% -> 80%` disk-pressure eviction. | Without MP4 expiration and 30-day secondary-frame pruning, 100 cameras exhaust a 1 TB drive in **18–30 days**. |
| **`obs_datastreams` Metadata Updates** | Every observation updated `resultTime` on `obs_datastreams`, generating millions of dead tuples/day and table bloat. | `fillfactor=50, toast_tuple_target=128` + `fastupdate=off` GIN indexes + redundant update suppression yield **`97.6%–98.4%` PostgreSQL HOT updates**; table stays **`< 2 MiB` (`5` lanes) / `5.4–6.2 MiB` (`50` lanes)** permanently. | Eliminated autovacuum storms and metadata lock contention during concurrent portal bursts. |
| **RTSP, HLS & Hybrid OCR Pipeline** | Direct per-consumer RTSP sockets dropped IP cameras, `Files.walk()` stalled HLS start/stop, and native FFmpeg `AVPacket` allocations leaked native heap. | Loopback **`MediaMTX`** holds **1 TCP socket per camera**, shares HLS across 64 viewers (`X-OSCAR-HLS-Viewer`), reuses a single pre-allocated `AVPacket`, and runs shared singleton ONNX **`CenterNet + CTC/PARSeq + DBNet` OCR (`~1.13 s/clip`)** under `OcrResourceGovernor`. | Prevents camera connection drops, native JNI heap leaks, and CPU starvation during burst transits. |
| **Server Container Memory (`cgroup v2`)** | Started at `~3.5 GiB`, climbed continuously via unbounded caches and native FFmpeg leaks until **`OutOfMemoryError` (`>8–16 GiB`)**. | **Flat `~1.4–2.0 GiB` (`5`–`6` OCR lanes) to `2.24 GiB` (`50` OCR lanes) `cgroup anon` process memory** (JVM + ONNX + FFmpeg inside `-Xmx4g`; `docker stats` additionally displays `~3.0–4.3 GiB` of kernel-reclaimable Linux `file` page cache); **`0` OOMs and `0` restarts**. | Eliminates server OOM crashes, GC stalls, and false alarms from Linux page-cache accounting. |
| **Operator Browser Memory (`oscar-viewer`)** | Eager `MqttTopicConnector` + unbounded Redux state leaked **`~0.5–1.5 GiB/day`**, crashing 24/7 wallboards in **24–48 hours**. | Shared 1-socket `MessagePort` WebSocket multiplexing (`acquireSharedConnection`), lazy stream connectors, and bounded event windows keep browser JS heap flat at **`~35–95 MB`** (`~180–260 MiB` total tab RSS). | Allows 24/7 command-center wallboards to run continuously without tab reloads or crashes. |
| **Long-Term Query & Report Latency** | $O(N)$ `OFFSET/LIMIT` & B-tree scans degraded as table size grew: `~400 ms` (Day 1) → `~5–8 s` (Month 1) → **`>30–60 s` / HTTP 504 timeouts (Month 6+)**. | **Bounded operational queries are $O(1)$ in total archive age:** `resultTime=latest` & 15d SQL summary counts (`oscar_obs_latest` + `oscar_archive_schema`) take **`40–130 ms`**, and bounded `1h–24h` cold/mixed Parquet queries take **`75–185 ms` on Ubuntu (`180–455 ms` on Windows WSL 2)** from Day 1 through Year 10. **Wide multi-month/annual report scans** scale linearly with queried span (`O(span)`: **`< 1–2 s/yr` on 5L, `~2–5 s/yr` on 50L** across `2` DuckDB threads). | Keeps live dashboards, alarm queues, and event detail lookups instantaneous regardless of whether the archive holds 1 day or 10 years of history, while bounding large historical report exports safely. |
